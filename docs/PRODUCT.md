# Product

Acceleratio - open source alternative to Railway, Render, Northflank and Vercel.

## Platform

web

## Users

Sovereign and regulated organizations that must run workloads and keep data on infrastructure they control.

The people using the console are the technical operators inside those organizations — platform and infrastructure engineers who install Acceleratio on their own cluster, create the first account, and then run and inspect the platform from a browser. Their job: stand the platform up without vendor help, and operate it while the control plane stays inside their own boundary.

Open decision: whether application developers outside that core operator team also get console access at launch.

## Product Purpose

Acceleratio is an open-source, self-hosted cloud platform. The console is its operator-facing surface: install the platform, sign in, and manage the organization's own infrastructure.

Near-term success: a new operator can install Acceleratio on their own cluster and reach first login without hand-holding.

## Positioning

Open-source, self-hosted PaaS — the deploy-and-operate experience of a managed platform, running entirely on the customer's own cluster, with data and the control plane staying inside the organization's infrastructure.

## Operating Context

- Installation targets a self-managed Kubernetes (k3s) cluster the operator controls. The verified reference deployment is a single Ubuntu 22.04, Ubuntu 24.04 or Debian 12 node that is both control plane and worker, provisioned by `deploy/install.sh` over SSH. More servers can be added, cordoned, drained and removed from the console's Servers page; that flow is not yet verified on a multi-node cluster.
- Docker services are published through k3s's bundled Traefik with Let's Encrypt certificates: one generated sslip.io domain per service and custom domains that go live once their A record points to the server. Ports 80 and 443 must be reachable from the internet. The local k3d cluster runs without Traefik, so domains cannot be served in local development.
- Every project is one private network. Each Docker service has a private name, `<hostname>.internal` (the slug of its name, editable), that every service of the same project reaches on any port; a database needs no public domain. The name never resolves in another project, and Cilium drops traffic between projects even by cluster IP or FQDN. It is always on and cannot be turned off. The name resolves to the current instances, so a client that caches the address must resolve it again after the target restarts. It needs k3s's CoreDNS (or a Corefile that imports `coredns-custom`). Separate networks inside a project are not offered.
- Docker services can mount up to 10 persistent volumes (1–100 GiB each) backed by SeaweedFS through the platform storage profile or a custom one. Volumes are part of the service config: they are created, re-pathed and deleted on deploy; a rollback restores everything else and leaves volumes as they are. A service with volumes is redeployed with the Recreate strategy, so two copies never write the same data, at the cost of a short pause on each deploy and restart. The size is a quota, not reserved space: volumes share the storage servers' free disk, and SeaweedFS fails every write once a volume is full, which can leave the file being written empty. Each volume shows how full it is on the service card and in Configuration, from the kubelet's volume stats in the bundled VictoriaMetrics, refreshed every minute; from 85% the card shows a warning and from 95% the bar turns red. Resizing a volume or moving it to another storage profile is not shipped yet. Profiles that retain data after deletion cannot back volumes.
- PostgreSQL databases (Basic) are created from the console with a version (16 or 17), a disk size and a storage profile, and run as one CloudNativePG instance; the CloudNativePG operator is part of the platform install. The overview shows the in-project connection address and, on request, the password, the server state and load, and the tables of the `app` database with their indexes and a read-only, paged view of their rows. A database can be stopped (hibernated), started and restarted; deleting it deletes its volume and data. Its volume sits on SeaweedFS like other volumes, which is slower than local disk and does not give a database the same durability on a power loss; treat Basic databases as single-instance without automatic failover. Settings can open the database port outside the cluster: closed by default, it becomes a node port (picked or chosen, 30000–32767) on the node that runs the database, limited to listed addresses or networks or explicitly to everyone, and connections from outside the pod network must use TLS (`sslmode=require`; the certificate is the cluster's own, so clients cannot verify it yet). The address follows the node, so it can change when the database moves. The canvas card shows the used and free space of its disk, with a warning from 85%. The disk can be grown from Settings (never shrunk) when the storage profile allows volume expansion; it grows in place without a restart. The password can be shown on request and regenerated after a confirmation: the database switches to it within seconds without touching data, and services that use the old one need the new value by hand (linked variables are not shipped yet). The project Observability tab adds a PostgreSQL row when the project has a database: client connections, transactions per second, cache hit ratio and the size of the `app` database over the selected range, one line per database, from CloudNativePG's built-in exporter scraped by the bundled VictoriaMetrics. Every database is backed up continuously: its WAL is archived as it is written and a base backup runs daily at 03:00 UTC (and on demand from the Backups tab), both gzip-compressed into a SeaweedFS bucket of its own that only its own keys can reach. Backups and WAL are kept 7 days, so the Backups tab can restore any moment from the first backup on into a new database in the same project with a new password; the source keeps running. WAL is sent when a segment fills or every 5 minutes, so a restore after losing the server can miss the last minutes. The bucket sits on the same SeaweedFS as the database: it protects against mistakes such as a dropped table, not against losing the server's disks. Backups are on by default and can be turned off on the Backups tab; turning them off, after a confirmation, stops archiving and deletes every backup with the bucket, and turning them on again starts from a new base backup. Deleting a database deletes its backups. The Backups tab also downloads the `app` database as it is now as a `pg_dump` custom-format file, streamed from the running instance whether backups are on or off; it needs `pg_restore` of the same PostgreSQL version or newer. It also imports a dump into the database as the `app` user (connected with its password, never as the superuser), all or nothing in one transaction: a custom-format archive replaces the objects it contains (pg_restore `--clean`), a SQL file runs as written, so it must be made with `pg_dump --no-owner --no-acl` (owners and grants of other roles fail and roll the import back). The file streams through the API into the instance; one import runs per database at a time, and very large files are held in the API's memory while they upload. Backups to an external S3 store, a configurable schedule or retention, restoring over the existing database, replicas, failover and connection pooling are not shipped yet.
- The installed release and the versions of its components are shown in Settings → System. The API checks GitHub Releases for newer stable releases every 6 hours and on demand. An update is started from the console without SSH: a privileged Job hands the release's checksum-verified `update.sh` to a systemd unit on the server. That unit backs up, updates, verifies and rolls back on failure, and the console follows its steps and log. Updates need internet access. There is no update channel other than stable, no offline bundle and no downgrade from the console yet, and there are no roles: any signed-in account can start an update.
- Settings → Integrations connects GitHub through GitHub Apps the operator owns. The console creates an App in one confirmation on github.com (the manifest flow), keeps its keys encrypted in the database, and installs it on accounts or organizations; several Apps can coexist. It works on the installer's IP address; GitHub delivers webhooks (uninstall, suspend) only to an HTTPS address, so without a control plane URL the App is created with its webhook off. A GitHub service follows a repository branch, picked from the repository's branches when it is created and changeable later in its settings (the next deploy builds the new branch's head), and runs like a Docker service (environment, volumes, domains, versions, logs). Deploy builds the `Dockerfile` at the root of the branch head with rootless BuildKit in the cluster, or, when there is none, a Railpack plan (the stack is detected from the source; the app must listen on its domain's port, for example through a `PORT` variable set on the service), pushes it to the in-cluster registry and deploys it; the overview lists builds with their log. A deploy whose image already comes from the branch head skips the build. A push to the branch deploys a service that was deployed before, unless its Deploy on push switch is off; a push during a build cancels it, and a build can be cancelled from the console. Pushes arrive only when the App's webhook is on, which needs an HTTPS address, and Apps created before push deploys must have the Push event enabled once in their settings on github.com. A Dockerfile path or build context other than the repository root, build arguments and build-time variables for Railpack builds are not shipped yet, and there are no roles, so any signed-in account can create or remove an App. GitHub Enterprise Server and entering an existing App's credentials by hand are not supported.
- Static sites are created from the console with a name and serve uploaded files over HTTPS on the same generated and custom domains as Docker services (port 80). An upload is a whole folder (or a set of files) with `index.html` at its top level; it is stored in SeaweedFS as a new release and deployed as a rolling update, so the old files keep being served until the new pods are ready, and Versions rolls back to an earlier upload's files. A `404.html` at the top level answers for missing paths; hidden files such as `.env` or `.git/` are never served. Deleting the project deletes its sites with their files. Each upload replaces every file: changing a single file, single-page-app fallback to `index.html`, redirects, custom headers, a size limit and deleting old uploads before the site is deleted are not shipped yet.
- Each project has a Logs tab: the stdout and stderr of all its Docker services in one time-ordered list, narrowed by service, pod, level and text, with a live mode that keeps following across deploys and restarts. Vector collects the lines into VictoriaLogs on the server's own disk, kept 7 days or up to 2 GiB, whichever comes first. A noisy pod is throttled at 2,000 lines/s at collection. Logs of the platform itself are not collected, and there are no saved searches, alerts or log export beyond downloading the loaded lines yet.
- Local development runs the console and API from source, with Postgres in Docker Compose.
- The console is a browser application; the API ("core") is a separate NestJS service; a shared package defines the typed contract between them.
- A fresh install begins with a one-time bootstrap step that creates the initial account, followed by normal sign-in.
- Buyers evaluate the product without a vendor account, managed service, or hosted dependency.

## Brand Commitments

- Name: Acceleratio. The console titles itself "Acceleratio Cloud Console" and renders the mark as the Acceleratio glyph followed by "cceleratio.cloud".
- Open source is a stated commitment, from the project README: "Acceleratio - Open Source Post Cloud Platform."
- Shipped voice, keep the register: direct, ownership-led, restrained — "Your cloud. Your data. Your control." and "Next-generation infrastructure. Private and secure by design." No hype or vendor-style superlatives.

## Product Principles

1. The organization that owns the metal owns the outcome: install, bootstrap, and operate without vendor involvement.
2. Self-hosting is the product, not a lesser edition of it.
3. The control plane stays inside the customer's boundary; no hidden dependency on a hosted service.
4. Show only what ships — planned sections are never presented as capability.
5. Procurement-grade rigor: accessibility and security claims are demonstrated, not asserted.

## Accessibility & Inclusion

Sovereign and regulated buyers impose procurement accessibility conformance. Treat WCAG 2.2 AA as the baseline, and expect documented conformance evidence for public-sector procurement; the specific target certification is not yet recorded.
